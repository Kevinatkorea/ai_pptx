# 멀티 프로젝트 광고 자동운영 시스템 계획서

> **문서 성격:** 사업·운영 계획서입니다. 개발계획서가 아닙니다.
> 아래 내용이 모두 확정된 뒤 개발계획서를 따로 작성합니다.
> **작성일:** 2026-10-08 · **상태:** 검토 중 (확정 필요 항목은 14장에 정리)

---

## 1. 목적

여러 프로젝트를 **동시에, 24시간** 운영하면서 정해진 예산 안에서 **ROAS를 지속적으로 높이는 것**이 목적입니다.

프로젝트 하나를 등록하면 아래 흐름이 자동으로 이어집니다.

> 시장조사 → 비즈니스 설계 → 추적 세팅 → 랜딩 A/B → 소재 생산 → 광고 집행 → 감시·최적화 → 분석 → CRM → (다시 처음으로)

사람은 **방향을 정하고, 돈이 더 나가는 결정을 승인하는 일**만 합니다.

## 2. 확정된 전제

| 항목 | 결정 내용 |
|---|---|
| 서버 | **iwinv 자체 서버 + MySQL** (Vercel 같은 외부 호스팅은 쓰지 않음) |
| 24시간 운영 장비 | **맥미니** (로컬) |
| 알림 | **전부 텔레그램 봇** |
| 광고 라이브러리 수집 | 메타, 구글 둘 다. API 제약이 있는 부분은 **맥미니에 설치한 Aside(AI 브라우저)**로 수집 |
| 수집 광고 분석 | 품질 검증을 통과하면 **맥미니 로컬 Qwen** 사용 (클로드 토큰 절약) |
| 소재 생성 | **클로드, 제미니, GPT, Higgsfield** API를 모두 연결하고, 작업 유형별로 적합한 모델을 자동 선택 |

## 3. 역할 분담: iwinv 서버 vs 맥미니

```
┌────────────── iwinv 서버 (외부 공개 영역) ──────────────┐
│ · 랜딩페이지 호스팅 + A/B 트래픽 분배                     │
│ · 전환 이벤트 수신 → 메타 전환API / GA4로 서버 측 전송     │
│ · MySQL (모든 프로젝트의 중앙 DB)                        │
│ · 맥미니 생존 감시 (맥미니 신호가 끊기면 텔레그램 발송)     │
└───────────────▲─────────────────────────┬─────────────┘
                │ 암호화 터널(SSH/VPN)       │ 서로 생존 확인
┌───────────────┴──── 맥미니 (내부 관제탑) ─▼─────────────┐
│ · 스케줄러: 15분~하루 단위 작업 실행                       │
│ · 수집: 메타/구글 광고 API, GA4, Aside(광고 라이브러리)     │
│ · 판정 엔진: 규칙 + AI 분석 → 조치 또는 승인 요청           │
│ · 로컬 LLM(Qwen): 광고 분류·태깅·요약                     │
│ · 생성 API 호출: 이미지·영상·카피                          │
│ · 텔레그램 봇: 알림, 승인 버튼, 명령어 처리                 │
└──────────────────────────────────────────────────────┘
```

**운영 원칙**
- **고객이 접속하는 것(랜딩, 전환 수신)은 iwinv에만 둡니다.** 맥미니가 꺼져도 광고와 랜딩은 그대로 돌아가고, 멈추는 것은 감시와 최적화뿐입니다.
- **MySQL은 외부에 직접 열지 않습니다.** 3306 포트를 공개하지 않고, 맥미니에서 암호화 터널로만 접속합니다.
- **두 장비가 서로를 감시합니다.**
  - 맥미니가 죽으면 → iwinv가 텔레그램으로 알립니다.
  - iwinv가 죽으면 → 맥미니가 알립니다.
  - 그래서 별도의 외부 감시 서비스가 필요 없습니다.

## 4. "결제·주문 데이터가 왜 필요한가?"

광고 플랫폼이 보고하는 성과는 **플랫폼이 추정한 숫자**입니다. 실제 매출과는 차이가 납니다. 주문 데이터(또는 신청·가입 데이터)는 아래 세 가지 이유로 필요합니다.

| 용도 | 설명 | 주문 데이터가 없으면 |
|---|---|---|
| **① 추적 고장 감지** | 실제 주문은 10건인데 픽셀에 잡힌 구매가 0건이면 추적이 고장 난 상태입니다. | 메타가 "전환이 없다"고 판단해 학습이 망가지고, 이 사실을 며칠 뒤에야 알게 됩니다. |
| **② 진짜 ROAS 계산** | 메타는 전환을 과다·중복으로 잡는 경우가 많습니다. 환불·취소도 반영하지 않습니다. | 플랫폼 ROAS가 300%여도 실제는 손익분기 미만일 수 있습니다. |
| **③ CRM 연결** | 누가 샀는지 알아야 재구매 유도, 구매자 제외 타겟팅, 유사 타겟을 만들 수 있습니다. | 9단계 CRM 자체가 불가능합니다. |

**결제가 없는 프로젝트**(상담 신청, 회원가입, 앱 설치 등)는 주문 대신 **해당 프로젝트의 실제 전환 기록**(신청 DB, 가입 DB)을 연결합니다.

핵심 원칙: **판단 기준은 플랫폼 숫자가 아니라 우리 DB의 숫자입니다.**

## 5. 단계별 운영 흐름

### 0단계 · 프로젝트 등록
- **입력:** URL, 소스 폴더, 광고계정·픽셀·GA4 ID, 마진율, 예산, 담당자 텔레그램
- **산출:** 프로젝트 설정 파일 1개
  - 이 파일 하나로 1~9단계가 자동 시작됩니다.
  - 새 프로젝트 추가 = 설정 파일 추가

### 1단계 · 시장조사 자동화
- 소스와 URL을 분석해서 서비스 내용, 강점, 차별점을 추출합니다.
- 경쟁사 목록과 최신 트렌드를 조사합니다.
- **메타·구글 광고 라이브러리**에서 경쟁사 광고를 수집하고 분석합니다 (상세는 8장).
- **산출:** 시장조사 리포트, 경쟁사 광고 DB

### 2단계 · 비즈니스 설계 (가치분석)
- 페르소나, 핵심 소구점 3~5개, 오퍼(할인·보너스·보증)를 설계합니다.
- **경제성 기준값을 산출합니다.**
  - 손익분기 ROAS = 1 ÷ 공헌이익률
  - 목표 ROAS, 목표 CPA
- 이후 모든 판정은 이 기준값으로 합니다.
- ✋ **사람 확인:** 소구점과 기준값을 승인

### 3단계 · 추적 인프라
- 순서: **GTM → GA4 → 메타 픽셀 → 전환API(iwinv 서버에서 전송) → API 테스트**
- **API 테스트 기준:** 테스트 주문을 넣었을 때 아래가 모두 일치해야 통과합니다.
  - 우리 DB 기록
  - 픽셀 이벤트
  - 전환API 이벤트 (중복 제거 확인)
  - GA4 이벤트
- 이 단계를 **통과하지 못하면 광고 집행 단계로 넘어갈 수 없습니다.**

### 4단계 · 랜딩페이지 (iwinv)
- 소구점별로 랜딩 변형을 만듭니다.
- iwinv 서버에서 방문자를 A/B로 나눠 보냅니다. 같은 방문자에게는 항상 같은 버전을 보여줍니다.
- 테스트는 **한 번에 한 변수만** 바꿉니다. 헤드라인, 오퍼, 구성 중 하나만 바꿔야 승자 판정이 가능합니다.

### 5단계 · 소재 생산
- 흐름: **레퍼런스(1단계 수집 광고) → 이미지 템플릿 → 이미지·영상 생성 → 디벨롭**
- 생성 모델 선택 기준은 10장을 따릅니다.
- ✋ **사람 확인:** 생성된 소재는 **"승인된 소재 풀"**에 들어간 것만 집행합니다.

### 6단계 · 광고 등록
- **규칙 설정 → 메타 광고 등록 → 구글 광고 등록**
- 초기 예산 배분: 테스트 70% / 스케일 30%
- 승자가 나오면 테스트 30% / 스케일 70%로 전환합니다.

### 7단계 · 24시간 감시·운영
- 6장과 7장 참고

### 8단계 · 데이터분석
- 우리 DB, 메타, 구글, GA4 데이터를 통합합니다.
- 프로젝트별 실제 ROAS를 산출합니다.
- 승자 소재와 승자 랜딩을 판정합니다.
- **포트폴리오 예산 재배분 제안:** 예산을 더 넣었을 때 효율이 덜 떨어지는 프로젝트로 예산을 옮기도록 제안합니다.

### 9단계 · CRM
- 장바구니 이탈 고객, 구매자 재구매 유도, 휴면 고객 재활성화
- 구매자는 신규 고객 광고 대상에서 제외합니다.
- 구매자 기반 유사 타겟을 만듭니다.
- 고객 LTV(평생 가치)를 2단계 목표 CPA 계산에 다시 반영합니다.
- 고객 발송 채널은 14장의 결정 항목입니다.

### 🔁 루프
- 8단계 결과를 1단계(조사), 4단계(랜딩), 5단계(소재)에 다시 넣어 다음 테스트를 설계합니다.

## 6. 24시간 감시

| 감시 대상 | 주기 | 이상 신호 |
|---|---|---|
| 광고비 소진 속도 | 15분 | 시간당 소진이 평소의 3배 초과 |
| 광고·계정 상태 | 15분 | 소재 거절, 계정 제한, 결제 수단 실패 |
| 추적 정상 여부 | 30분 | 실제 전환은 있는데 픽셀·전환API 이벤트가 0건, 또는 30% 넘게 차이 |
| 랜딩페이지 | 1~5분 | 접속 불가, 응답 4초 초과, 결제·신청 단계 오류 |
| MySQL·서버 | 5분 | 디스크 90% 초과, DB 연결 실패 |
| 성과 (실제 ROAS, CPA) | 하루 3회 | 3일 기준 CPA가 목표의 1.5배 초과, ROAS가 이틀 연속 손익분기 미만 |
| 소재 피로도 | 하루 1회 | 빈도 3 초과, CTR이 초기 대비 40% 하락 |
| 경쟁사 광고 | 하루 1회 | 신규 광고 급증, 30일 이상 장기 집행 소재 등장 |

> ⚠️ **사고 감시와 성과 판정을 분리합니다.**
> - **사고(돈, 상태, 추적, 랜딩)**는 실시간으로 감시합니다.
> - **성과(ROAS, CPA)**는 하루~3일 단위로 판정합니다.
>
> 메타 전환 데이터는 늦게 들어오기 때문에, 오전에 ROAS가 낮아 보인다고 광고를 끄면 멀쩡한 광고를 죽이게 됩니다.

## 7. 텔레그램 알림 체계와 자동조치

### 7-1. 채널 구성
텔레그램 **그룹 하나에 "주제(토픽)" 기능**을 켜고 아래처럼 나눕니다.

| 토픽 | 내용 |
|---|---|
| 🚨 긴급 | 모든 프로젝트의 P1 알림을 한곳에 모음 |
| 📁 프로젝트별 토픽 | 프로젝트마다 하나씩. P2~P4 알림 |
| ✅ 승인 대기 | 예산 증액, 새 소재 집행 요청 |
| 📊 리포트 | 일간·주간 리포트 |

### 7-2. 알림 등급

| 등급 | 상황 | 방식 |
|---|---|---|
| **P1 긴급** | 예산 폭주, 계정 정지, 랜딩 다운, 추적 0건, 맥미니·서버 다운 | 즉시 발송. **확인 버튼을 누를 때까지 5분마다 재발송** |
| **P2 경고** | 성과 기준 이탈, 소재 거절 | 즉시 발송 (새벽에는 아침에 묶어서) |
| **P3 승인 요청** | 돈이 더 나가는 조치 | [승인] [거절] 버튼 |
| **P4 리포트** | 일간·주간 성과 | 정해진 시간에 발송 |

### 7-3. 텔레그램 명령어 예시
| 명령어 | 동작 |
|---|---|
| `/status` | 전체 프로젝트 현황 |
| `/status 프로젝트명` | 해당 프로젝트 상세 |
| `/stop 프로젝트명` | 해당 프로젝트 광고 전체 즉시 정지 (킬스위치) |
| `/resume 프로젝트명` | 재개 |
| `/report` | 즉시 리포트 |

> ⚠️ **텔레그램만 쓸 때의 위험:** 휴대폰이 무음이거나 텔레그램 알림이 꺼져 있으면 P1을 놓칩니다.
> 대응책:
> - 🚨 긴급 토픽만 **방해금지 예외 + 전용 알림음**으로 설정합니다.
> - 확인할 때까지 반복 발송합니다.
> - 30분 동안 미확인이면 **안전 조치(해당 프로젝트 광고 일시정지)를 자동 실행**할지 결정이 필요합니다 → 14장

### 7-4. 자동조치 범위

**원칙: 돈을 덜 쓰는 조치는 자동, 더 쓰는 조치는 승인**

| 레벨 | 자동 실행 | 승인 필요 |
|---|---|---|
| Level 1 | 감시와 알림만 | 모든 조치 |
| **Level 2 (시작 단계)** | 성과 나쁜 소재 OFF, 예산 폭주 시 일시정지 | 예산 증액, 새 소재 집행 |
| Level 3 | 하루 20% 이내 증액, 승인 소재 풀에서 자동 교체 | 한도 상향, 새 캠페인 |

**안전장치**
- **하드캡 이중화:** 시스템의 프로젝트별·전체 일 한도 + 메타 광고계정 자체 지출 한도
- **수정 제한:** 같은 광고세트는 하루 2회까지만 수정 (학습 리셋 방지)
- **변경 이력:** 모든 자동조치를 "언제, 무엇을, 왜" 기록하고 되돌릴 수 있게 함

## 8. 광고 라이브러리 수집 (메타 + 구글)

### 8-1. 공식 API의 한계
| 구분 | 메타 광고 라이브러리 | 구글 광고 투명성 센터 |
|---|---|---|
| 공식 API | 일반 상업 광고는 EU 노출분과 정치·사회 이슈 광고 위주로만 조회 가능. **국내 상업 광고 조회는 제한적** | **공식 API 없음** |
| 결론 | 웹 화면에서 수집 필요 | 웹 화면에서 수집 필요 |

### 8-2. 수집 방식: 맥미니 + Aside
- **Aside는 AI 에이전트가 내장된 크롬 기반 브라우저**입니다. 사람이 브라우저를 쓰듯 웹페이지를 열고, 검색하고, 내용을 정리합니다.
- 맥미니에 설치하고, 스케줄에 맞춰 수집 작업을 실행합니다.
  - 예시 작업: "경쟁사 A의 메타 광고 라이브러리에서 현재 집행 중인 광고 전체의 소재, 카피, 시작일, 랜딩 URL을 정리"
- 결과는 MySQL에 저장하고, 소재 이미지와 영상 파일은 맥미니에 저장합니다.

**Aside 도입 시 확인할 점**
- **초기 단계 제품입니다** (YC F25). 업데이트에 따라 동작이 바뀔 수 있습니다.
- **예약 실행·자동화 지원 수준:** 사람 없이 정해진 시간에 작업을 돌릴 수 있는지 확인이 필요합니다.
- **요금제별 사용량 한도:** 무료 / Pro 월 $20 / Max 월 $200으로 알려져 있으며, 공식 사이트에서 재확인이 필요합니다.
- **수집 전용 프로필 사용:** 광고 계정이나 개인 계정이 로그인된 프로필로 수집하지 않습니다. 계정 제재 위험을 차단하기 위해서입니다.
- **수집 속도 제한:** 요청 빈도를 낮게 유지하고, 각 플랫폼 이용약관을 확인합니다.
- **대체 수단 확보:** Aside가 실패할 때를 대비합니다.
  - 메타: 크롤링 서비스(Firecrawl, Apify 등)
  - 구글: SerpApi 투명성 센터 엔진 등

### 8-3. 수집 항목과 분석 포인트
- **수집 항목:** 광고주, 플랫폼·지면, 소재(이미지/영상), 카피, **집행 시작일과 기간**, 같은 메시지의 변형 수, 랜딩 URL
- **분석 포인트**
  - **30일 이상 계속 집행 중인 광고 = 경쟁사의 "돈 버는 소재"**입니다. 레퍼런스 우선순위 1위로 둡니다.
  - 같은 메시지를 여러 버전으로 돌리고 있다면 경쟁사가 지금 테스트 중인 소구점입니다.
  - 분류 기준: 후킹 유형(문제 제기 / 혜택 / 후기 / 비교 / 권위), 포맷, 오퍼, CTA
- 경쟁사 소재는 **분석용으로만 씁니다.** 그대로 복제하지 않습니다 (저작권·상표 리스크).

## 9. AI 분석 모델 역할 분담 (로컬 Qwen vs 클로드)

### 9-1. 분담 원칙
**반복적이고 양이 많은 일은 로컬 Qwen, 판단과 전략이 필요한 일은 클로드**가 맡습니다.

| 작업 | 담당 | 이유 |
|---|---|---|
| 수집 광고 분류·태깅 (후킹 유형, 포맷, 오퍼) | **로컬 Qwen** | 양이 많고 기준이 정해진 작업 |
| 소재 이미지 속 문구 추출, 이미지 설명 | **로컬 Qwen 비전 모델** | 동일 |
| 영상 광고 분석 | **로컬 Qwen 비전 모델** | 영상에서 핵심 장면만 뽑아 이미지로 분석 |
| 일간 수치 요약, 이상 신호 1차 설명 | **로컬 Qwen** | 정형 데이터 요약 |
| 시장조사 결론, 소구점 도출, 전략 제안 | **클로드** | 종합적 판단이 필요 |
| 랜딩 카피, 광고 카피 | **클로드** | 한국어 설득 문장의 품질 차이가 큼 |
| 주간 인사이트, 다음 테스트 설계 | **클로드** | 종합적 판단이 필요 |

### 9-2. 품질 검증 방법 (도입 전 1회)
1. 수집 광고 200건을 **Qwen과 클로드에 똑같이** 분류시킵니다.
2. 결과 일치율을 비교합니다.
   - **90% 이상 → Qwen 채택**
   - 미만 → 해당 작업은 클로드 유지, 또는 Qwen에 예시를 더 주고 재검증
3. 이후 **월 1회 20건 표본을 다시 검증**합니다. 모델이나 수집 데이터가 바뀌어 품질이 떨어지는지 확인하기 위해서입니다.

### 9-3. 맥미니 사양 기준
- **텍스트·비전 모델을 동시에 쓰려면 메모리 48GB 이상**을 권장합니다 (M4 Pro 64GB면 여유).
- 32GB 맥미니는 작은 모델(9B급)만 쾌적하게 돌아갑니다. 분류 품질이 떨어질 수 있습니다.
- 실행 방식: 맥에서는 **MLX 기반 실행**이 Ollama 기본 실행보다 빠르다는 보고가 있습니다. 도입 시 실제 속도를 직접 측정해 결정합니다.

## 10. 소재 생성 모델 선택 기준

### 10-1. 중요 전제
**클로드는 이미지·영상 생성 기능이 없습니다.** 그래서 소재 생산에서 클로드의 역할은 다음과 같습니다.
- 소재 기획 (어떤 소구점을 어떤 장면으로 보여줄지)
- 각 생성 모델에 맞는 **프롬프트 작성**
- 광고 카피 작성
- 생성된 결과물 **검수** (브랜드 일치, 금지 표현, 한글 오류 확인)

### 10-2. 작업 유형별 1순위 모델 (2026년 10월 조사 기준)

| 작업 유형 | 1순위 | 대안 | 선택 이유 |
|---|---|---|---|
| 문구가 많은 배너 (가격, 헤드라인) | **GPT Image 2 계열** | Ideogram | 이미지 속 글자 정확도가 가장 높다는 평가 |
| 제품 실사, 라이프스타일 사진 | **Gemini Nano Banana 2** | GPT Image 2 | 실사 질감, 빠른 속도, 낮은 비용 |
| 대표 메인 이미지 (고품질 1장) | **Gemini Nano Banana Pro** | GPT Image 2 | 복잡한 장면 구성에 강함 |
| 대량 변형 (색상, 배경, 비율 바꾸기) | **Gemini Nano Banana 2** | – | 비용과 속도 |
| 제품 사진 → 짧은 영상 | **Higgsfield** (내부에서 Kling, Seedance 등 선택) | Gemini Veo 3.1 | 원본 제품 모양 유지가 중요 |
| 고급 브랜드 영상 | **Gemini Veo 3.1** | Higgsfield 경유 Kling | 영상미와 부드러운 움직임 |
| 저비용 대량 숏폼 | **Higgsfield 경유 Seedance** | – | 초당 단가가 가장 낮은 편 |
| 말하는 사람이 나오는 영상 (UGC형) | **Higgsfield** (AI 인플루언서, 립싱크) | Seedance | 입 모양 맞추기 특화 |

> 💡 **한글 문구는 이미지 생성 모델에 맡기지 않습니다.**
> 생성 모델은 한글을 자주 깨뜨립니다. 그래서 **배경과 제품 이미지만 생성하고, 한글 카피는 이미지 템플릿 위에 따로 합성**합니다.
> 이렇게 하면 오타가 없고, 문구만 바꿔 A/B 테스트하기도 쉽습니다.

### 10-3. 자동 선택(라우팅) 규칙
1. 5단계에서 클로드가 소재 기획서를 만들 때 작업 유형을 지정합니다.
2. 시스템이 위 표에 따라 1순위 모델로 생성합니다.
3. 생성 실패나 검수 탈락이 나오면 대안 모델로 재시도합니다.
4. **모델 재평가는 월 1회 합니다.**
   - 같은 기획서를 모든 모델로 생성해 비교합니다.
   - **실제 광고 성과(CTR, CPA)가 쌓이면 성과 데이터 기준으로 1순위를 교체합니다.**
   - 생성 AI 모델은 몇 달 단위로 바뀌기 때문에 표를 고정하지 않습니다.
5. **모델별·프로젝트별 생성 비용을 기록합니다.** 소재 1개당 비용 대비 성과를 봅니다.

## 11. 데이터 분석과 리포트

- **기준 데이터:** 우리 DB(실제 주문·신청) > GA4 > 광고 플랫폼 순으로 신뢰합니다.
- **일간 리포트 (텔레그램, 매일 오전):** 프로젝트별 광고비, 실제 매출, 실제 ROAS, 전일 대비 변화, 어제 실행된 자동조치
- **주간 리포트:** 승자·패자 소재, 랜딩 A/B 결과, 다음 주 테스트 제안(클로드 작성), 예산 재배분 제안
- **대시보드:** iwinv 서버에 관리자 전용 웹페이지를 둘지는 결정 필요 (14장). 리포트만으로 운영할 수도 있습니다.
