> **상태:** 검토 중 (확정이 필요한 항목은 15장에 정리)

| 버전 | 날짜 | 변경 내용 |

## 1. 목적

여러 프로젝트를 **동시에, 24시간** 운영하면서 정해진 예산 안에서 **ROAS를 지속적으로 높이는 것**이 목적입니다.

프로젝트를 하나 등록하면 아래 흐름이 자동으로 이어집니다.

> 시장조사 → 비즈니스 설계 → 추적 세팅 → **랜딩 확보(기존 페이지 활용 + 신규 추가)** → 소재 생산 → 광고 집행 → 감시·최적화 → 분석 → CRM → (다시 처음으로)

사람이 하는 일은 두 가지입니다.
- 방향을 정합니다.
- **돈이 더 나가거나 운영 중인 서비스를 바꾸는 결정을 승인**합니다.

## 2. 확정된 전제

| 항목 | 결정 내용 |
|---|---|

| 랜딩 | **기존 서비스 페이지를 랜딩으로 쓰는 것이 기본**입니다. 광고 성격에 맞는 페이지가 없으면 해당 서비스 안에 **랜딩을 추가**합니다 |
| **프로젝트 작업 폴더** | **`D:\META_AD`** (Windows PC). 계획서, 설정, 소스를 이곳에서 관리하고, 완성된 실행본은 맥미니에 배포 |
| 24시간 운영 장비 | **맥미니** (로컬) |
| 알림 | **전부 텔레그램 봇** |
| 광고 라이브러리 수집 | 메타, 구글 모두. API 제약이 있는 부분은 **맥미니에 설치한 Aside(AI 브라우저)**로 수집 |
| 수집 광고 분석 | 품질 검증을 통과하면 **맥미니 로컬 Qwen** 사용 (클로드 토큰 절약) |
| 소재 생성 | **클로드, 제미니, GPT, Higgsfield** API를 연결하고, 작업 유형별로 적합한 모델을 자동 선택 |

## 3. 역할 분담: iwinv 서버 2대 vs 맥미니

```
┌──── iwinv 서버 1 ────┐   ┌──── iwinv 서버 2 ────┐
│ 프로젝트 A, B 서비스   │   │ 프로젝트 C, D 서비스   │   ← 고객이 접속하는 영역
│ · 기존 페이지 = 랜딩   │   │ · 기존 페이지 = 랜딩   │
│ · /lp/ 추가 랜딩       │   │ · /lp/ 추가 랜딩       │
│ · A/B 트래픽 분배      │   │ · A/B 트래픽 분배      │
│ · 전환API 서버 전송    │   │ · 전환API 서버 전송    │
│ · 서비스 MySQL         │   │ · 서비스 MySQL         │
└─────────▲────────────┘   └─────────▲────────────┘
          │ SSH 키 접속 (전용 계정, 제한된 권한)  │
┌─────────┴───────── 맥미니 (관제탑) ───────────┴─────────┐
│ · 서버·서비스 분석, 랜딩 후보 진단, 랜딩 생성·배포·되돌리기 │
│ · 스케줄러, 수집기(광고 API, GA4, Aside), 판정 엔진        │
│ · 로컬 LLM(Qwen), 생성 API 호출                          │
│ · 마케팅 운영 DB (MySQL)                                 │
│ · 텔레그램 봇: 알림, 승인 버튼, 명령어                     │
└──────────────────────────────────────────────────────┘
       서버 1 ↔ 서버 2 ↔ 맥미니: 서로 생존 확인
```

### 운영 원칙

**① 고객이 접속하는 것(서비스, 랜딩, 전환 수신)은 iwinv에만 둡니다.**
- 맥미니가 꺼져도 광고와 랜딩은 정상으로 돌아갑니다.
- 멈추는 것은 감시와 최적화뿐입니다.

**② 마케팅 운영 데이터와 서비스 데이터를 분리합니다.**
- 서비스 MySQL에서는 **주문·신청 데이터를 읽기만** 합니다.
- 마케팅 데이터(광고 성과, 소재, 판정 기록)는 별도 DB에 둡니다.
- 운영 중인 서비스 DB에 마케팅 테이블이 섞이지 않게 하기 위해서입니다.
- 마케팅 DB의 위치(맥미니 또는 서버 중 1대)는 결정 항목입니다 → 15장

**③ 세 장비가 서로를 감시합니다.**
- 서버 1, 서버 2, 맥미니 중 어느 하나가 응답하지 않으면 나머지가 텔레그램으로 알립니다.

**④ MySQL은 외부에 직접 열지 않습니다.**
- 3306 포트를 공개하지 않습니다.
- 맥미니에서는 SSH 터널로만 접속합니다.

## 4. "결제·주문 데이터가 왜 필요한가?"

광고 플랫폼이 보고하는 성과는 **플랫폼이 추정한 숫자**입니다. 실제 기록과 비교해야 하는 이유는 세 가지입니다.

| 용도 | 설명 | 주문 데이터가 없으면 |
|---|---|---|
| **① 추적 고장 감지** | 실제 주문은 들어왔는데 픽셀 구매 이벤트가 0건이면 추적이 고장 난 상태입니다 | 메타 학습이 망가진 것을 며칠 뒤에야 알게 됩니다 |
| **② 진짜 ROAS 계산** | 플랫폼 전환에는 과다·중복 집계가 있고, 환불·취소는 반영되지 않습니다 | 플랫폼 ROAS가 300%여도 실제로는 손해일 수 있습니다 |
| **③ CRM 연결** | 누가 샀는지 알아야 재구매 유도, 구매자 제외, 유사 타겟을 만들 수 있습니다 | 10단계 CRM이 불가능합니다 |

- 결제가 없는 프로젝트(상담 신청, 회원가입 등)는 **신청·가입 DB**를 대신 연결합니다.
- **판단 기준은 플랫폼 숫자가 아니라 우리 DB 숫자입니다.**

## 5. 단계별 운영 흐름

### 0단계 · 서버·프로젝트 등록
- **입력:** 서버 접속 정보(6-1 보안 원칙을 따름), 프로젝트별 도메인, 광고계정·픽셀·GA4 ID, 마진율, 예산, 담당자 텔레그램
- **자동 분석:** 서버 2대를 스캔해서 **"서버·서비스 지도"**를 만듭니다 (6-2)
  - 어느 서버에 어떤 프로젝트가 있는지
  - 각 서비스의 기술 구성
  - DB 위치
  - 현재 설치된 추적 코드
- **산출:** 프로젝트 설정 파일. 이 파일을 기준으로 1~10단계가 실행됩니다.

### 1단계 · 시장조사
- 서비스 소스와 실제 페이지를 분석해서 **서비스 강점과 차별점**을 추출합니다.
- 경쟁사와 최신 트렌드를 조사합니다.
- **메타·구글 광고 라이브러리**를 수집·분석합니다 (9장).
- 경쟁사 광고가 연결된 **경쟁사 랜딩 구조**도 함께 분석합니다.

### 2단계 · 비즈니스 설계 (가치분석)
- 페르소나, 핵심 소구점 3~5개, 오퍼를 설계합니다.
- 경제성 기준값을 산출합니다.
  - 손익분기 ROAS = 1 ÷ 공헌이익률
  - 목표 ROAS
  - 목표 CPA
- ✋ **사람 확인:** 소구점과 기준값 승인

### 3단계 · 추적 인프라
- 순서: GTM → GA4 → 메타 픽셀 → 전환API(iwinv 서버에서 전송) → **API 테스트**
- 테스트 주문 1건이 아래 네 곳에 모두 일치해서 찍혀야 통과합니다.
  - 우리 DB
  - 픽셀
  - 전환API (중복 제거 포함)
  - GA4
- **통과 전에는 광고를 집행하지 않습니다.**
- **기존 서비스의 결제 완료, 가입 완료 시점에 전환 이벤트를 연결하는 작업**이 이 단계에 포함됩니다.

### 4단계 · 랜딩 확보 ★ v2 신규
- 6장의 체계를 따릅니다.
- **기존 페이지 진단 → 소구점별 랜딩 배정 → 부족한 랜딩 추가 → A/B 구성**

### 5단계 · 소재 생산
- 흐름: 레퍼런스 → 이미지 템플릿 → 이미지·영상 생성 → 디벨롭
- **소재는 연결될 랜딩의 첫 화면과 메시지를 맞춰서 만듭니다** (6-4 메시지 일치 원칙).
- 생성 모델 선택은 11장을 따릅니다.
- ✋ **사람 확인:** 승인된 소재 풀에 들어간 것만 집행합니다.

### 6단계 · 광고 등록
- 순서: 규칙 설정 → 메타 광고 등록 → 구글 광고 등록
- 모든 광고 URL에 **UTM 규칙을 자동 적용**합니다. 어떤 광고가 어떤 랜딩으로 가서 얼마나 팔았는지 추적하기 위해서입니다.
- 초기 예산 배분: 테스트 70% / 스케일 30%
- 승자가 나오면 테스트 30% / 스케일 70%로 전환합니다.

### 7단계 · 24시간 감시·운영
- 7장, 8장 참고

### 8단계 · 데이터분석
- 우리 DB, 광고 플랫폼, GA4를 통합합니다.
- 프로젝트별 실제 ROAS를 계산합니다.
- **소재 × 랜딩 조합별 성과**를 분석합니다.
- 포트폴리오 예산 재배분을 제안합니다.

### 9단계 · 랜딩 개선 루프
- 성과가 낮은 랜딩은 개선안을 만들어 A/B 테스트에 넣습니다.
- 승자 랜딩은 상시 운영으로 전환합니다.

### 10단계 · CRM
- 장바구니 이탈, 재구매, 휴면 고객 재활성화
- 구매자를 신규 고객 광고에서 제외합니다.
- 구매자 기반 유사 타겟을 만듭니다.
- 고객 LTV를 목표 CPA 계산에 다시 반영합니다.

### 🔁 루프
- 8단계와 9단계 결과를 1단계(조사), 4단계(랜딩), 5단계(소재)에 다시 반영합니다.

## 6. 랜딩페이지 운영 체계 ★ v2 신규

### 6-1. 서버 접속 보안 원칙

서버 접속 정보를 받기 전에 아래 원칙부터 확정합니다.

| 원칙 | 내용 |
|---|---|
| **채팅에 비밀번호를 붙여넣지 않음** | 접속 정보는 대화창이나 문서로 주고받지 않습니다. 맥미니의 키체인(암호 보관함)에 직접 등록합니다 |
| **전용 계정 사용** | root 계정을 쓰지 않습니다. 서버마다 **마케팅 전용 계정**을 새로 만듭니다 |
| **비밀번호 대신 SSH 키** | 맥미니의 SSH 키로만 접속합니다. 접속할 수 있는 IP를 맥미니로 제한하는 것도 권장합니다 |
| **최소 권한** | 서비스 소스는 **읽기만** 가능. 쓰기는 **랜딩 전용 폴더(`/lp/`)에만** 허용 |
| **DB 권한 분리** | 서비스 DB는 **주문·신청 테이블 읽기 전용 계정**만 사용합니다 |
| **기존 페이지 수정 = 별도 승인** | 기존 서비스 파일을 바꾸는 작업은 매번 텔레그램 승인을 받고, 백업한 뒤에만 실행합니다 |
| **모든 작업 기록** | 서버에서 실행한 명령과 변경한 파일을 전부 기록합니다 |

### 6-2. 서버·서비스 지도 (최초 1회 + 변경 시 갱신)

맥미니가 서버 2대에 접속해서 아래 정보를 자동으로 정리합니다.

| 항목 | 예시 |
|---|---|
| 서버별 프로젝트 목록 | 서버 1: A, B / 서버 2: C, D |
| 도메인 ↔ 소스 폴더 연결 | a.com → /var/www/a |
| 웹서버 / 기술 구성 | Nginx 또는 Apache / PHP, 그누보드, 워드프레스, Laravel, Node 등 |
| 페이지 목록 | 실제 접속 가능한 모든 URL (사이트 크롤링 + 소스 라우팅 분석) |
| 전환 지점 | 결제 완료, 가입 완료, 신청 완료 페이지와 그 데이터가 저장되는 DB 테이블 |
| 현재 추적 상태 | GTM, GA4, 픽셀 설치 여부, 중복 설치 여부 |
| 서버 여유 자원 | CPU, 메모리, 디스크, 트래픽 (광고 유입이 늘었을 때 버틸 수 있는지) |

**랜딩 추가 방식은 기술 구성에 따라 달라집니다.** 그래서 이 지도가 있어야 6-5의 방식을 프로젝트별로 정할 수 있습니다.

### 6-3. 기존 페이지 랜딩 진단

서비스의 모든 페이지를 아래 기준으로 점수화해서 **"랜딩 후보 목록"**을 만듭니다.

| 진단 항목 | 확인 내용 |
|---|---|
| 메시지 적합도 | 2단계 소구점과 첫 화면 내용이 맞는지 (AI 판정) |
| 첫 화면 구성 | 스크롤하지 않아도 헤드라인, 핵심 혜택, 행동 버튼이 보이는지 |
| 모바일 | 모바일 화면 깨짐, 버튼 크기, 가로 스크롤 여부 |
| 속도 | 모바일 첫 화면 표시 3초 이내 여부 |
| 전환 경로 | 결제·신청까지 몇 번 클릭해야 하는지, 중간에 이탈 요인(회원가입 강제 등)이 있는지 |
| 추적 | 해당 페이지에서 픽셀과 GA4가 정상 작동하는지 |
| 신뢰 요소 | 후기, 인증, 보증, 사업자 정보 노출 여부 |
| 광고 정책 | 과장·금지 표현이 있는지 (메타 광고 심사, 표시광고법 기준) |

**판정 결과**
- 🟢 **그대로 사용:** 해당 소구점 광고의 랜딩으로 바로 배정
- 🟡 **보완 후 사용:** 개선점 목록을 만들고, 기존 페이지 수정 승인 요청
- 🔴 **부적합:** 신규 랜딩 추가 대상

### 6-4. 광고 성격별 랜딩 유형

**메시지 일치 원칙:** 광고에서 약속한 내용이 랜딩 첫 화면에 그대로 보여야 합니다.
- "첫 구매 50% 할인" 광고 → 랜딩 첫 화면 헤드라인도 "첫 구매 50% 할인"
- 메시지가 어긋나면 이탈률이 올라가고, 메타 광고 품질 점수도 떨어집니다.

| 광고 성격 | 맞는 랜딩 유형 | 기존 페이지로 대체 가능한 경우 |
|---|---|---|
| 상품 직접 판매 | **상품 상세형** (혜택 → 증거 → 구매) | 상품 상세페이지가 잘 되어 있으면 그대로 사용 |
| 할인·이벤트 | **혜택 집중형** (오퍼 + 마감 시간) | 이벤트 페이지가 있으면 사용 |
| 상담·신청 (리드) | **신청 폼형** (짧은 폼, 첫 화면에 폼 배치) | 대부분 신규 추가 필요 |
| 문제 인식 유도 | **기사형(어드버토리얼)** (문제 → 해결책 → 상품) | 보통 신규 추가 |
| 비교·검토 단계 고객 | **비교·후기형** (경쟁 대안과 비교, 후기 집중) | 후기 페이지 일부 활용 |
| 참여 유도 | **퀴즈·진단형** (질문 3~5개 → 맞춤 추천) | 신규 추가 |
| 리타겟팅 (방문 후 이탈자) | **마무리형** (추가 혜택, 자주 묻는 질문, 보증) | 신규 추가 권장 |
| 브랜드 인지 | **메인·브랜드 소개** | 메인 페이지 사용 |

### 6-5. 랜딩 추가 방식

**원칙: 같은 서비스 안에, 같은 도메인으로 추가합니다.**

| 방식 | 예시 | 장점 | 단점 |
|---|---|---|---|
| **① 같은 도메인 하위 경로 (권장)** | `a.com/lp/summer-sale` | 픽셀·쿠키·도메인 인증이 그대로 유지됨. 기존 장바구니·결제와 바로 연결 | 서비스 웹서버 설정을 일부 바꿔야 할 수 있음 |
| ② 같은 도메인의 서브도메인 | `lp.a.com/summer-sale` | 기존 서비스와 완전히 분리되어 안전 | 로그인·장바구니 연결이 까다로울 수 있음 |
| ③ 기존 서비스 기능으로 추가 | 워드프레스나 그누보드에서 페이지 생성 | 서비스 관리 화면에서 보임 | 서비스마다 방식이 다르고 자동화가 어려움 |

**신규 랜딩 구성 원칙**
- **기존 서비스의 디자인을 그대로 씁니다.** 헤더, 푸터, 색상, 글꼴을 가져옵니다. 같은 브랜드로 보여야 신뢰가 유지됩니다.
- **결제와 신청은 기존 서비스 흐름으로 연결합니다.** 랜딩은 "설득"만 담당합니다. 결제는 기존 장바구니·결제로 넘깁니다. 그래야 주문 데이터가 기존 DB에 그대로 쌓입니다.
- **블록 조립 방식으로 만듭니다.** 첫 화면, 혜택, 증거(후기·수치), 오퍼, 자주 묻는 질문, 행동 버튼 블록을 2단계 소구점에 맞춰 조립합니다. 그러면 변형 버전을 빠르게 만들 수 있습니다.
- **검색엔진에 노출하지 않습니다(noindex).** 광고 전용 페이지가 기존 페이지의 검색 순위에 영향을 주지 않도록 하기 위해서입니다.
- **추적 코드는 기존 서비스와 같은 GTM 컨테이너를 씁니다.** 이벤트 이름도 통일합니다.

### 6-6. 배포 절차 (운영 중인 서비스 보호)

```
① 생성 → ② 미리보기 경로에 배포 → ③ 자동 점검 → ④ 텔레그램 승인 → ⑤ 실제 배포 → ⑥ 배포 후 점검
                                            │                              │
                                       (미리보기 링크 +                (문제 발생 시
                                        모바일 화면 캡처)               즉시 자동 되돌리기)
```

**③ 자동 점검 항목**
- 화면 정상 표시 (PC, 모바일)
- 표시 속도
- 링크·버튼 동작
- 결제·신청 연결
- 픽셀·GA4 이벤트 발생
- 금지 표현 검사

**백업과 되돌리기**
- 모든 배포 전에 **변경 대상 파일을 백업**합니다.
- 서버의 랜딩 폴더는 **버전 관리(Git)**합니다.
- 텔레그램 `/rollback 랜딩명` 한 번으로 이전 버전으로 돌아갑니다.

**기존 페이지 수정 규칙 (🟡 판정)**
- 소스를 직접 고치기보다 **A/B 분배 장치로 수정본을 일부 방문자에게만 보여주는 방식**을 우선합니다.
- 수정본이 이기면 그때 기존 페이지에 반영합니다. 이때도 승인을 받습니다.

**배포 금지 시간대**
- 트래픽이 많은 시간대에는 배포하지 않습니다. 프로젝트별로 시간을 설정합니다.

### 6-7. A/B 트래픽 분배

**서버에서 나눕니다.** 화면에서 스크립트로 나누면 화면이 깜빡이고 속도가 느려집니다.
- 웹서버 설정 또는 서비스 코드에서 처리합니다. 6-2에서 확인한 기술 구성에 따라 결정합니다.
- 같은 방문자에게는 항상 같은 버전을 보여줍니다 (쿠키로 고정).
- 버전 정보가 GA4와 주문 데이터에 함께 저장되어야 합니다. 그래야 **버전별 실제 매출**을 비교할 수 있습니다.

**승자 판정 기준**
- 버전별 최소 전환 수를 확보합니다 (기본 100건, 프로젝트 규모에 따라 조정).
- 최소 7일간 운영합니다 (요일별 차이 반영).
- **한 번에 한 가지 요소만 바꿉니다.**

### 6-8. 랜딩 등록부와 수명 관리

모든 랜딩을 DB에 등록하고 상태를 관리합니다.

| 상태 | 의미 |
|---|---|
| 후보 | 진단은 끝났지만 아직 광고에 연결하지 않음 |
| 테스트 | A/B 테스트 중 |
| 운영 | 승자. 광고에 상시 연결 |
| 종료 | 성과 부진 또는 이벤트 종료 |

**종료된 랜딩은 삭제하지 않고 메인이나 상품 페이지로 자동 연결(리다이렉트)합니다.** 아직 돌고 있는 광고나 공유된 링크가 오류 페이지로 가는 것을 막기 위해서입니다.

등록부에는 랜딩마다 아래 정보를 기록합니다.
- 연결된 광고 목록
- 소구점
- 랜딩 유형
- 버전 이력
- 성과 (방문 → 전환율 → 실제 매출)

## 7. 24시간 감시

| 감시 대상 | 주기 | 이상 신호 |
|---|---|---|
| 광고비 소진 속도 | 15분 | 시간당 소진이 평소의 3배 초과 |
| 광고·계정 상태 | 15분 | 소재 거절, 계정 제한, 결제 수단 실패 |
| 추적 정상 여부 | 30분 | 실제 전환은 있는데 픽셀·전환API가 0건, 또는 30% 넘게 차이 |
| **광고 중인 랜딩 전체** | 1~5분 | 접속 불가, 응답 4초 초과, 결제·신청 단계 오류 |
| **랜딩 내용 변경 감지** | 1시간 | 다른 사람의 서비스 수정으로 랜딩 내용·버튼·추적 코드가 바뀌거나 사라짐 |
| **서버 2대 자원** | 5분 | CPU·메모리 과부하, 디스크 90% 초과, DB 연결 실패 |
| 성과 (실제 ROAS, CPA) | 하루 3회 | 3일 기준 CPA가 목표의 1.5배 초과, ROAS가 이틀 연속 손익분기 미만 |
| 소재 피로도 | 하루 1회 | 빈도 3 초과, CTR이 초기 대비 40% 하락 |
| 경쟁사 광고 | 하루 1회 | 신규 광고 급증, 30일 이상 장기 집행 소재 등장 |

> ⚠️ **사고 감시와 성과 판정은 분리합니다.**
> - 사고(돈, 상태, 추적, 랜딩, 서버)는 실시간으로 봅니다.
> - 성과(ROAS, CPA)는 하루~3일 단위로 판정합니다.
> 메타 전환 데이터는 늦게 들어오기 때문에, 오전 숫자만 보고 광고를 끄면 멀쩡한 광고를 죽이게 됩니다.

**랜딩 다운 시 자동조치**
- 그 랜딩으로 연결된 광고를 **자동으로 일시정지**합니다.
- 접속이 안 되는 페이지에 광고비가 나가는 것을 막기 위해서입니다.
- 랜딩이 복구되면 재개 승인을 요청합니다.

## 8. 텔레그램 알림 체계와 자동조치

### 8-1. 채널 구성
텔레그램 그룹 하나에 **토픽 기능**을 켜고 아래처럼 나눕니다.

| 토픽 | 용도 |
|---|---|
| 🚨 긴급 | 모든 프로젝트의 P1 알림 |
| 🖥 서버 | 서버 1, 서버 2, 맥미니 상태 |
| 📁 프로젝트별 | 프로젝트마다 1개 |
| ✅ 승인 대기 | 예산 증액, 소재 집행, **랜딩 배포, 기존 페이지 수정** |
| 📊 리포트 | 일간·주간 |

### 8-2. 알림 등급

| 등급 | 상황 | 방식 |
|---|---|---|
| **P1 긴급** | 예산 폭주, 계정 정지, 랜딩·서버 다운, 추적 0건 | 즉시 발송. **확인 버튼을 누를 때까지 5분마다 재발송** |
| **P2 경고** | 성과 기준 이탈, 소재 거절, 랜딩 내용 변경 감지 | 즉시 발송 (새벽에는 아침에 묶어서) |
| **P3 승인 요청** | 돈이 더 나가는 조치, 서비스 변경 | [승인] [거절] 버튼 + 미리보기 링크·캡처 |
| **P4 리포트** | 일간·주간 성과 | 정해진 시간에 발송 |

### 8-3. 명령어

| 명령어 | 동작 |
|---|---|
| `/status`, `/status 프로젝트명` | 전체 또는 프로젝트별 현황 |
| `/stop 프로젝트명` | 해당 프로젝트 광고 즉시 전체 정지 (킬스위치) |
| `/resume 프로젝트명` | 광고 재개 |
| `/landings 프로젝트명` | 랜딩 목록, 상태, 성과 |
| `/rollback 랜딩명` | 랜딩을 이전 버전으로 되돌리기 |
| `/report` | 즉시 리포트 |

> ⚠️ **텔레그램만 쓸 때의 위험:** 휴대폰이 무음이면 P1을 놓칠 수 있습니다.
> - 🚨 긴급 토픽은 방해금지 예외 + 전용 알림음으로 설정합니다.
> - 확인할 때까지 반복 발송합니다.
> - 30분 동안 확인이 없으면 자동으로 일시정지할지는 결정 항목입니다 → 15장

### 8-4. 자동조치 범위

**원칙**
- 돈을 덜 쓰는 조치는 자동으로 실행합니다.
- 돈을 더 쓰는 조치와 **운영 중인 서비스를 바꾸는 조치**는 승인을 받습니다.

| 레벨 | 자동 실행 | 승인 필요 |
|---|---|---|
| Level 1 | 감시와 알림만 | 모든 조치 |
| **Level 2 (시작)** | 성과 나쁜 소재 끄기, 예산 폭주·랜딩 다운 시 일시정지, 문제 생긴 랜딩 자동 되돌리기 | 예산 증액, 새 소재, 랜딩 배포, 기존 페이지 수정 |
| Level 3 | 하루 20% 이내 증액, 승인된 소재 풀에서 교체, **승인된 템플릿 기반 랜딩 변형 배포** | 한도 상향, 새 캠페인, 기존 페이지 수정 |

**기존 서비스 페이지 수정은 어떤 레벨에서도 자동으로 하지 않습니다.**

**안전장치**
- **하드캡 이중화:** 시스템의 일 한도 + 메타 광고계정 자체 지출 한도
- **수정 횟수 제한:** 같은 광고세트는 하루 2회까지만 수정 (학습 리셋 방지)
- **변경 이력:** 모든 자동조치를 기록하고, 되돌릴 수 있게 합니다

## 9. 광고 라이브러리 수집 (메타 + 구글)

### 9-1. 공식 API의 한계

| 구분 | 메타 광고 라이브러리 | 구글 광고 투명성 센터 |
|---|---|---|
| 공식 API | 일반 상업 광고는 EU 노출분, 정치·사회 이슈 광고 위주. **국내 상업 광고 조회는 제한적** | **공식 API 없음** |
| 결론 | 웹 화면에서 수집 필요 | 웹 화면에서 수집 필요 |

### 9-2. 수집 방식: 맥미니 + Aside
- **Aside는 AI 에이전트가 들어 있는 크롬 기반 브라우저**입니다. 맥미니에 설치하고 스케줄에 맞춰 수집을 시킵니다.
- 결과 데이터는 마케팅 DB에, 소재 파일은 맥미니에 저장합니다.

**도입 시 확인할 점**
- **초기 단계 제품입니다** (YC F25).
- **사람 없이 예약 실행이 되는지** 확인이 필요합니다.
- 요금제: 무료 / Pro 월 $20 / Max 월 $200으로 알려져 있습니다. 공식 사이트에서 다시 확인해야 합니다.
- **수집 전용 브라우저 프로필**을 씁니다. 광고 계정이나 개인 계정이 로그인된 상태로 수집하지 않습니다.
- 수집 속도는 낮게 유지하고, 각 플랫폼 이용약관을 확인합니다.
- **Aside가 실패할 때의 대체 수단**
  - 메타: Firecrawl, Apify 같은 크롤링 서비스
  - 구글: SerpApi 투명성 센터 엔진 등

### 9-3. 수집 항목과 분석 포인트

**수집 항목**
- 광고주
- 지면
- 소재
- 카피
- 집행 시작일과 기간
- 변형 수
- **랜딩 URL과 랜딩 구조**

**분석 포인트**
- **30일 이상 계속 집행 중인 광고는 경쟁사의 "돈 버는 소재"입니다.** 레퍼런스 1순위로 둡니다.
- 같은 메시지를 여러 버전으로 돌리고 있다면, 경쟁사가 지금 테스트 중인 소구점입니다.
- **경쟁사 랜딩 유형을 분석합니다** (상세형인지, 기사형인지, 퀴즈형인지). 이 결과를 6-4 랜딩 유형 선택에 반영합니다.
- 경쟁사 소재와 랜딩은 **분석용으로만** 씁니다. 그대로 복제하지 않습니다.

## 10. AI 분석 모델 역할 분담 (로컬 Qwen vs 클로드)

| 작업 | 담당 |
|---|---|
| 수집 광고 분류·태깅, 이미지 속 문구 추출, 영상 핵심 장면 분석 | **로컬 Qwen** (텍스트 + 비전) |
| 일간 수치 요약, 이상 신호 1차 설명 | **로컬 Qwen** |
| 서비스 페이지 크롤링 결과의 1차 정리 (페이지 목록, 구성 요약) | **로컬 Qwen** |
| 시장조사 결론, 소구점, 전략 | **클로드** |
| **랜딩 진단의 최종 판정, 랜딩 카피, 랜딩 구성안** | **클로드** |
| 광고 카피, 주간 인사이트, 다음 테스트 설계 | **클로드** |
| **서버 소스 분석, 랜딩 코드 생성** | **클로드** (코드 품질과 기존 서비스 안전이 중요) |

**품질 검증 (도입 전 1회)**
1. 수집 광고 200건을 Qwen과 클로드에 똑같이 분류시킵니다.
2. 결과 일치율이 **90% 이상이면 Qwen을 채택**합니다.
3. 이후 월 1회 20건 표본으로 다시 검증합니다.

**맥미니 사양**
- 텍스트 모델과 비전 모델을 함께 돌리려면 **메모리 48GB 이상**을 권장합니다 (64GB면 여유).
- 실행 방식(MLX 또는 Ollama)은 실제 속도를 측정한 뒤 정합니다.

## 11. 소재 생성 모델 선택 기준

### 11-1. 전제
**클로드에는 이미지·영상 생성 기능이 없습니다.** 클로드는 아래 일을 맡습니다.
- 소재 기획
- 모델별 프롬프트 작성
- 카피 작성
- 결과물 검수

### 11-2. 작업 유형별 1순위 모델 (2026년 10월 조사 기준)

| 작업 유형 | 1순위 | 대안 |
|---|---|---|
| 문구가 많은 배너 | **GPT Image 2 계열** | Ideogram |
| 제품 실사, 라이프스타일 | **Gemini Nano Banana 2** | GPT Image 2 |
| 고품질 대표 이미지 | **Gemini Nano Banana Pro** | GPT Image 2 |
| 대량 변형 (색, 배경, 비율) | **Gemini Nano Banana 2** | – |
| 제품 사진 → 짧은 영상 | **Higgsfield** (Kling, Seedance 등) | Gemini Veo 3.1 |
| 고급 브랜드 영상 | **Gemini Veo 3.1** | Higgsfield 경유 Kling |
| 저비용 대량 숏폼 | **Higgsfield 경유 Seedance** | – |
| 사람이 말하는 UGC형 영상 | **Higgsfield** (AI 인플루언서, 립싱크) | Seedance |
| **랜딩 첫 화면 이미지** | 해당 광고 소재와 **같은 모델·같은 장면**으로 생성 | – |

> 💡 **한글 문구는 생성 모델에 맡기지 않습니다.** 이미지만 생성하고, 한글 카피는 템플릿 위에 따로 합성합니다. 랜딩도 마찬가지로, 이미지 위에 글자를 박지 않고 HTML 텍스트로 넣습니다.

### 11-3. 자동 선택 규칙
1. 클로드가 기획서에 작업 유형을 지정합니다.
2. 1순위 모델로 생성합니다.
3. 생성에 실패하거나 검수에서 떨어지면 대안 모델로 다시 만듭니다.
4. **월 1회 모델을 재평가합니다.** 실제 광고 성과(CTR, CPA) 기준으로 1순위를 바꿉니다.
5. 모델별·프로젝트별 생성 비용을 기록합니다.
